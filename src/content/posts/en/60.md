For anyone who has been writing software for a few years, git has become something like air, a tool so pervasive that it is no longer perceived as a choice. That is exactly why it is striking to read that Anthropic has replaced it in its monorepo with Scion, a version control system built in house by a team of seven people in about five months. It sounds like the story of a company reinventing the wheel, but Anthropic's account shifts the focus from git as a tool to the kind of load git was designed for. The bottleneck, the company explains, is no longer writing code but the infrastructure around it, from source control to the continuous integration pipeline, both sized for developers who make a few commits a day and not for swarms of agents that produce thousands. It should not be confused with Google's Scion, a testbed for orchestrating agents in containers that uses git and has nothing to do with this project.

##### The numbers that broke git

The figures explain better than any theoretical argument why the classic solutions stopped being enough. In May 2026 the monorepo received about 2,500 merged changes a day, by September there were more than 30,000, with a main branch history exceeding 100 GB and a compressed working copy above 25 GB. Continuous integration alone performs about 25 million checkouts a day, not counting agent sandboxes and development environments. If each of these clients downloaded the repository naively, traffic would exceed 600 PB a day. For years Anthropic held on with the classic arsenal, shallow clones, sparse checkout, promisor remotes and several hundred internal mirrors, but every increase in the merge rate made those mirrors more fragile, and trivial operations such as diff and blame on partial clones became an exercise in patience.

##### An opposite starting assumption

The difference between git and Scion does not lie in a single algorithm but in the assumption each one starts from. Git assumes that every machine holds a complete copy of the history and that work can happen offline, computing commits, rebases, blame and merges locally and then synchronizing with a push. Scion reverses the model and assumes an authoritative server and always connected clients, which own nothing and request data at the moment they need it. In this world commits and rebases happen directly on the server, so there is nothing to push, while history and blame are exposed through APIs. Free branches and tags are discouraged, except for main and release branches, and the working copy becomes optional and sparse, with files materialized only when needed. The most instructive comparison concerns data transfer: in git the client declares what it already has and the server prepares a packfile with the difference, an archive that at this scale can weigh several GB, whereas in Scion the client starts from the root tree and walks down requesting only the directories and files it needs, getting small responses that can be resumed if the connection drops.

##### How it works under the hood

The unit of work in Scion is the changeset, a row in a write-ahead log that, unlike a git commit pointing to an entire tree, lists only the files changed relative to the first parent and refers to their compressed content in blob storage through an address computed from the content itself. History and blame are derived data, computed by walking up the parents, and the client never sees the details, so Anthropic can change them without touching developer tooling. References are updated with a compare-and-swap on a single Spanner row, separately from changeset creation, and since all other data is immutable any server can cache it without coordinating with the others. The architecture has three tiers speaking the same RPCs, a scion-daemon on every node, in-memory regional caches and authoritative servers reading from Spanner or cloud storage, in a deliberately rigid hierarchy that prevents a struggling cache from pushing the problem upstream. With no packfiles to optimize, repository maintenance disappears as well, and the reported results mention cache hit rates above 99% at every tier, an infrastructure 200 times smaller than the old mirrors, checkouts going from minutes to seconds and a quarter of CI CPU capacity recovered, internal numbers that cannot be verified from the outside.

##### Claude's role in building it

The handwritten prototype of the pipeline that imports history from git was rewritten by Claude Mythos Preview, using twenty times less memory and running four times faster, while preserving the implicit invariants of the original code. The engineers' work shifted accordingly towards defining architecture, trade-offs and constraints, frequently rejecting proposals that violate system constraints or are simply overengineered, with reviews that look at the intent of a change more than at individual lines. Alongside Scion came Antique, a code review tool whose approvals can distinguish a change that only touches comments from one that alters logic. On merging, Anthropic gave up on a global lock, impossible to sustain at this scale, and relies on tests run after merge and before deploy, letting Claude resolve most conflicts before a human even notices them.

##### Why it is not a git replacement

The most useful part for anyone working with git every day is the caution of Anthropic itself, which describes Scion as unsuitable for general use and sensible only for gigantic monorepos, with tens of thousands of engineers or swarms of agents, and which has published neither its code nor a repository. The path is not new either, since Google has long followed a centralized model with Piper and Meta open sourced the Sapling client in 2022. What is new is what drives the change, namely the volume of code produced by agents, along with the prediction that problems of this kind will become common within six to twelve months. This is why the company proposes bringing some of Scion's ideas into git, with servers offering complete APIs and different negotiation protocols, working together with GitHub, GitLab and the open source community. For a team with a repository of a few GB and a dozen developers nothing changes today and git remains the right tool, but the signal about direction is hard to ignore: if agents write a growing share of the code, the limits show up in the infrastructure before they show up in the models, and anyone designing systems would do well to ask which of their tools is still sized for human rhythms.
